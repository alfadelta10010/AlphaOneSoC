toivoh [TT], Role icon, tested tapeout — 12/24/25, 11:48 AM
If you use start bits and headers as I did in pio-ram-emulator, you get some overhead. It only uses 2 TX pins and 2 RX pins, but it would be hard to get much higher speed for 16 bit transactions even with more pins, due to the overhead.
For the retro console, there is no overhead: 4 address bits sent in one direction and 4 data bits in the other, every cycle (the sync is established once at startup). That kind of scheme allows you to scale up the bandwidth better. I'm sure there's a way to make a read/write scheme out of it, but I haven't looked into the details.
toivoh [TT], Role icon, tested tapeout — 12/24/25, 12:24 PM

RebelMikeRole icon, contributor — 12/31/25, 2:06 PM
Interesting idea! There are a couple of issues though.

You’d need to have a tri state buffer to be able to disable the output from the asic to the QSPI when you wanted the PSRAM to drive them, which might mess with timing, and also needs an extra pin for the enable. Although maybe you could just use resistors?

The other problem is that you can only select a PSRAM for a relatively short amount of time, as it needs to perform memory refresh which it can’t do while selected. This is likely shorter than a scanline. You probably need a true SRAM with a QSPI interface.
toivoh [TT], Role icon, tested tapeout — 12/31/25, 2:50 PM
Then there's of course the drawback that unless you make your Pmod generally available somehow, nobody else will be able to try you design. But that shouldn't stop you unless you want it to.
