RebelMikeRole icon, contributor — 11/7/24, 12:05 AM
The SPI RAM emulation on the RP2040 is currently limited to standard SPI, so one bit per clock.  It's also fairly slow and the RAM available is limited to 128kB at most.  Max speed is documented here: https://github.com/MichaelBell/spi-ram-emu

You would probably be better targeting the QSPI PMOD, which provides QSPI access to 16MB flash and 16MB PSRAM.  It should be available to ship as an add-on with the TT demo board: https://github.com/mole99/qspi-pmod

The flash part used can do DTR, so that gets you up to 8 bits per SPI clock.  Doing 16 bits per cycle would need to use a lot of your available pins.

In answer to your questions:
1) The SYS clock documented on the SPI RAM emulation README is the RP2040 system clock. This is only related to your project clock in that if the RP2040 is providing your project clock the project clock would be an even divider of the RP2040 system clock
2) The SPI SCLK is provided by the SPI controller in your design.
3) It might be possible to use the 8 bidir pins for data and do double data rate from the RP2040. But this wouldn’t be straightforward and might further reduce the max SCLK.
4) I think it’s relatively straightforward to tweak the SPI pinout on the RP2040 side.

TroyburnRole icon, contributor — 11/7/24, 11:28 PM
To give some kind of response here:
Going above 25MHz with SPI CLK will introduce turn-around-propagation delay concerns (as the mux has latency in both directions).
Going above 25MHz with SPI CLK means you are basically connecting the global CLK pin (maybe via a clock-gate cell) to the SPI CLK output.  I think projects have shared the pin and used SPI CS to enable/disable (to not bother with using another pin for SPI CLK output if it is exactly the same signal as global CLK, even with latency/skew differences with doing that).

Going SPI with 8bit data path with DDR (Double-Data-Rate) looks possible on paper (but still have potential concerns above approx 25MHz SPI CLK rates).  This would also leave pins available for UART and single-direction GPIO.

Obviously these ideas might exceed limits for emulation, but you could make the design work at slower clock rates in that scenario and make things switch-able/automatic (use a different SPI command for 1bit, 4bit, 8bit data transfer in SDR or DDR load/store commands and switch between).  This would allow the RP2040 emulator to work at the same time as the possibility of a real 8bit DDR capable SPI chip, as well as a cheaper simple 1bit SDR SPI chip.  But obviously more complex/more planning/design/testing is needed to make all that work in a single design.

The simple design approach is to accept a 50MHz global clock and use DFF to halve the SPI CLK to 25MHz and operate SPI.  But this is the opposite of your expressed design goals (of fast RAM, slow CPU), but reducing 50MHz down (for slower CPU clock) is possible trivially. 
RebelMikeRole icon, contributor — 11/7/24, 11:46 PM
On pinouts: The limit here is the IOs connected to your design.  There are 8 bidirs, 8 outputs and 10 inputs (including clk and reset).  That's all you get - it doesn't matter which PMODs you're using on the demo board to access them!

On changing the SPI pinout of the emulated SPI, I don't have instructions for that, the PIO assembler would need tweaking.  Currently I have two versions.  Both require the input pins to be consecutive, one in order MOSI, SCK, CS (in the spi-ram-emu repo) and the other MOSI, CS, SCK (here: https://github.com/MichaelBell/micropython/blob/sim_spi_ram/ports/rp2/sram.pio).  MISO and MOSI can be any pin.

Though again note the RP2040 emulated RAM is currently limited to 1-bit, single data rate SPI at a max of about 20MHz (and even that requires overclocking the RP2040).
