toivoh [TT], Role icon, tested tapeout — 6/3/26, 6:01 PM
I have never used the PSRAM, but I've done a lot of VGA output at around 25.2 MHz by clicking at around 50.4 MHz and updating every other cycle, that is no problem. And it shouldn't be a problem for other IO signals that you want to pretend are half of the clock frequency either. Also, my impression is that VGA displays usually have some tolerance around the target pixel clock. Mine seems to tolerate that I go down to 60% of the nominal pixel clock or maybe even a bit lower and still looks quite ok, but I don't know how representative that is.
TT gpio output is limited to around outputting max a 33 MHz clock or so. That means that it's ok to output a signal that is sampled at up to 66 MHz (a 33 MHz clock can be seen as a square wave sampled at 66 MHz).
For the PSRAM, I've heard that there is some refresh timing that you have to beware, which means that you can't keep the interface busy for too many cycles at a time, which can be troublesome for some VGA projects. Maybe @RebelMike or @pongsagon knows more about it.
I've been using the RP2040 (RP2350 on the new boards)  as RAM emulator instead, see e g https://github.com/toivoh/tt06-retro-console and https://github.com/toivoh/pio-ram-emulator. It also has its limitations, but not related to max number of accesses in a row.

RebelMikeRole icon, contributor — 6/3/26, 7:01 PM
Yes, the APS6404 PSRAM on the TT QSPI PMOD has a max chip select time of 8us, which is significantly shorter than a 640x480 scanline.  It's possible you will get away with a longer select time, but this may cause the data to read incorrectly after the max selection time, and could possibly also cause data corruption as you're blocking the RAM from refreshing.  Whether this causes a problem in practice I'm not sure - potentially you don't care if the odd bit is flipped on a display so don't need to be as careful as if you were reading instructions for a CPU.  Personally, I would probably split the scanline in half and have sufficient buffer to do one read restart during the scanout - that would still be reading for longer than the spec allows, but likely short enough not to cause issues in practice.

The other consideration is making sure you generate a clean clock.  This should be fine as long as it comes directly from the output from a flop without any other logic between the flop and the output pin.  If there is any logic then you would need to understand whether the cells involved might cause unexpected transients (that doesn't matter so much on a data line, but does on a clock).

Thanks for your responses! Good to know that using the 50 MHz clock with an every-other-cycle enable for VGA has worked on real TT hardware.

For the PSRAM, we are not planning to keep CS low for a full scanline. We read short bursts into two ping-pong buffers and release CS between transactions. Right now each burst is 8 bytes at 25 MHz SCK, so the data portion should be 16 SCK cycles, around 640 ns. Even with the command/address/dummy cycles added, each transaction should still be well under the 8 us limit.

The controller also inserts a short CS-high gap between transactions. In the back-to-back case this should be at least roughly one to two SCK cycles, around 40–80 ns at 25 MHz, and if there are no pending read/write requests it idles with CS high for longer. During active VGA scanout, the reads can happen frequently to keep the buffers filled, but CS is still released after each burst rather than being held low continuously.

We also changed the PSRAM clock output so it comes from a registered flop output, not through combinational logic. We have the PSRAM connected to our FPGA setup at the moment, and this method seems to work well there.

Does this approach sound like it addresses the main PSRAM concerns you mentioned? or is there anything else you think we should watch out for on the real TT hardware? Thanks again!
